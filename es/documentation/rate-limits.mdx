Los límites de solicitudes en la API de ER:LC Rusia son **personalizados y dinámicos**: se configuran mediante el sistema de políticas, pueden variar según la dirección IP o el nivel de la clave API, y aumentan automáticamente con los beneficios de suscripciones activas.

La tabla a continuación muestra los **valores base predeterminados**. Los límites reales aplicados a su aplicación se definen exclusivamente a través de las cabeceras de respuesta del servidor. Se recomienda a clientes y bots no fijar números estáticos en el código, sino orientarse dinámicamente por las cabeceras `X-RateLimit-*`.

## Rutas estándar

| Grupo | Límite base |
|---|---|
| `/v3/cdn/*`, `/v3/user-assets/*`, `/v3/users`, `/v3/keys`, `/v3/points/*`, `/v3/health` | 20 solicitudes por minuto |
| `/v3/erlc/*`, `/v3/civops/*`, `/v3/subscriptions/*`, `/v3/ads/*` | 120 solicitudes por minuto |
| `/v3/stats` sin clave de API | 40 solicitudes por minuto |
| `/v3/stats` con clave de API | 120 solicitudes por minuto |
| `/v3/ai/*` | 120 solicitudes por segundo |

Las rutas estándar comparten un contador por clave entre métodos y rutas; sin credenciales se usa la IP. AI tiene una ventana independiente de un segundo. Comprobar un archivo mediante GET y subirlo mediante POST cuenta como dos solicitudes. Al alcanzar el límite, detenga el envío y repita únicamente la solicitud rechazada tras la espera indicada en las cabeceras.

## Autorización

El inicio de sesión OAuth y sus callbacks permiten 10 solicitudes por minuto por usuario con cookie de sesión firmada. Las demás rutas de autenticación del usuario permiten 250 por sesión o 60 por visitante anónimo.

Las solicitudes anónimas tienen además un límite compartido por IP: 120 por minuto para iniciar sesión y 240 para las demás rutas de autenticación. La ventana se reinicia al comenzar cada minuto.

## Cómo orientarse por las cabeceras (HTTP Headers)

En cada solicitud, la API devuelve un conjunto de cabeceras que describen el estado de su cuota:

| Cabecera | Descripción | Cómo debe usarla el cliente |
|---|---|---|
| `X-RateLimit-Limit` | Límite asignado para la ventana activa | Muestra el límite personalizado de su clave según políticas y suscripciones |
| `X-RateLimit-Remaining` | Número de solicitudes restantes | Si se acerca a `0`, el cliente debe ralentizar el envío de solicitudes (client-side throttling) |
| `X-RateLimit-Reset` | Momento de reinicio (marca de tiempo Unix en ms) | Indica el instante exacto en que la cuota `Remaining` se restablece por completo |
| `Retry-After` | Tiempo de espera requerido en segundos (con `429`) | Pausa obligatoria antes de reintentar la solicitud rechazada |

```json
{
  "code": 5016,
  "message": "Rate Limit Exceeded",
  "retry_after": 30,
  "details": {"limit": 20, "count": 21, "excess": 1, "reset_at": 1792083600000}
}
```

El limitador de autenticación omite details. Un bloqueo por spam del middleware estándar devuelve code=5039, message=spam_blocked, blocked_until y remaining_seconds. La ventana estándar tiene un umbral de 400 solicitudes excedentes y un bloqueo base de cinco minutos; AI usa un umbral de 200 solicitudes excedentes por segundo.

El limitador no convierte las modificaciones en operaciones idempotentes. Tras una interrupción de red, compruebe primero el estado del recurso. Un conflicto de ruta explícita en CDN devuelve 409; no es un 429 ni confirma una sobrescritura correcta.

## Protección de Cloudflare

Cloudflare también puede rechazar o bloquear solicitudes independientemente de los límites de la API, incluido un gran volumen desde una sola IP. No existe un umbral universal garantizado de 10.000 solicitudes por segundo: depende de las reglas de seguridad y las características del tráfico. [Cloudflare](https://developers.cloudflare.com/waf/rate-limiting-rules/).
