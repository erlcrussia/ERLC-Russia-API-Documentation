Порядок релізу: складання з новим RELEASE_ID, послідовне завантаження файлів, перевірка SHA-256 та HTTP, потім перемикання HTML на нове складання. Старі чанки зберігайте для відкритих вкладок. Ключі зберігайте лише у секретах CI/CD.

## Підтверджений кастомний домен

Надайте точні шляхи файлів у JSON paths, максимум 100. Не використовуйте query prefix: цей маршрут його не підтримує. Відсутня або порожня paths означає весь домен.

```bash
curl -X POST "$API_BASE/v3/cdn/webhook/purge" \
  -H "erlcrussia-api-cdn-token: $CDN_DEPLOY_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"paths":["releases/RELEASE_ID/logo.png"]}'
```

З ключом користувача той же JSON відправляється в `POST /v3/cdn/custom-domains/{id}/purge` через заголовок erlcrussia-api-key.

Відповідь містить success, domain, cloudflarePurged, edgePurged та timestamp. HTTP 200 не гарантує успіху: success=false означає помилку одного або обох рівнів. Перевірити кожен прапор. Браузерний кеш цим запитом не очищується.

## Звичайний namespace та групи файлів

`POST /v3/cdn/assets/purge?domain=YOUR_TEAM_SLUG&prefix=releases/RELEASE_ID/` приймає prefix та планує очищення кешу CDN. Це інший контракт. Без ids/path/prefix вибирається весь namespace. success означає прийняття операції; перевіряйте наступну доставку.

Новий URL релізу надійніше заміни старого immutable-файлу. HTTP 429 вимагає очікування Retry-After; HTTP 409 означає існуючий об'єкт, а не успішне завантаження.

Без ids/path/prefix очищення всього namespace виконується у фоні: HTTP 202, status=queued, acceptedCount — кількість вибраних об’єктів, а не завершених. Один запит на хвилину на команду та namespace; при 429 враховуйте Retry-After. Результат записується в аудит API. Точкове очищення зберігає HTTP 200 і purgedCount. Нові унікальні URL релізу зазвичай не потребують purge одразу після завантаження: це видаляє прогрітий кеш.
